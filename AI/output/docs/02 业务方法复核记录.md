## 1. 模式与业务的两个维度

先识别业务边界，再在每个业务内按用例需要选写入、域内读、外部读、规则计算、纯计算。DomainService归业务，本域可有多个服务，不强制每模式一个服务。当前业务有五个子域，数量碰巧与模式数量相同，不能据此建立对应关系。

| 业务 | 实际领域服务 | 保存/清理 | 应用职责 |
|---|---|---|---|
| auth | AuthDomainService | 5保存+RefreshReceipt清理 | AuthWrites/AuthWriteApplicationAssembler/AuthRepositories；登录与账号提交序列 |
| chat | ChatDomainService | 4保存 | ChatWrites/ChatWriteApplicationAssembler/ChatRepositories；对话和模型调用记录 |
| memory | MemoryDomainService | 3保存+MemoryFactSource清理 | MemoryWrites/MemoryWriteApplicationAssembler/MemoryRepositories；提取/删除生命周期 |
| knowledge | KnowledgeDomainService | 3保存 | KnowledgeWrites/KnowledgeWriteApplicationAssembler/KnowledgeRepositories；上传/索引 |
| sync | SyncDomainService | 2保存+SyncEvent清理 | SyncWrites/SyncWriteApplicationAssembler/SyncRepositories；事件/发件箱 |

所有Param归domain/<业务>/model/param，领域服务只依赖同业务仓储。原全局TravelWriteDomainService、DomainWrites、TravelWriteApplicationAssembler、TravelRepositories和旧persistence包已删除，没有兼容路由。清理14个无调用物理删除入口及Param，保留20实际操作；WriteDO仅是共享结果标记，ApplicationFailures.required仅验证技术失败契约。

## 2. 全项目范围与完整链路

[294源文件分类](verification/vertical-class-inventory.csv)、[790方法/构造器](verification/vertical-method-inventory.csv)、[782构造位置](verification/vertical-constructor-inventory.csv)全量建立清单，371多语句流程块，默认有限门禁0违规。输入/应用/输出/持久化映射边界、层内异常、编号/方法规模与此前重构的对象不变量继续保持；静态分类不是语义证明。

AuthFlow使用auth写/读协作，SyncEvents单独接sync协作；Transactions以auth账号序列协调提交。ChatFlow域内普通读直接chat仓储、写入经chat领域；MemoryFlow/PrivacyCleanup在应用层显式协同memory和chat；后台保留流程显式协同auth和sync；知识检索/索引在应用层使用knowledge与auth读取及外部端口。各域服务无其他域仓储，无中央路由；Spring离线装配验证没有循环依赖。

20个保留操作的规则方法体AST与拆分前相同，既有归属、版本、删除状态、目标缺失与CAS保持。17领域实体、仓储接口和PersistenceConverter未改，正式MySQL V1 SHA不变。当前结构改变所有相关消费者与装配，并删除未使用依赖，避免只重命名而维持隐藏的大总服务。

## 4. 为什么此前未发现

我把开发模式误用为业务边界，并在后续复核中只确认有限规则和转换位置，未核对域内所有依赖与跨域组织。这是建模和审查遗漏，不能归因为用户没有描述或以静态门禁通过辩解。通用规范1.14的DDD-009～012以业务归属、对象命名与完整链路复核纠正，当前测试提供本项目反例证据，不规定其他项目必须有相同业务域或服务数量。
